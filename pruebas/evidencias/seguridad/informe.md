# Informe de pruebas de seguridad — TaskFlow API

- **Fecha de ejecución:** 2026-10-26T23:19:11.367Z
- **Herramienta:** Node.js v20.20.2 test runner (node:test) + fetch nativo; npm 10.8.2 audit; psql (PostgreSQL 18) para verificación de solo lectura
- **Comando:** `cd pruebas/seguridad && npm test   (equivale a: node run.js → node --test seguridad.test.js)`
- **Condiciones:** API http://localhost:3000 (NestJS en modo desarrollo, PostgreSQL 18 local), frontend http://localhost:5173; Windows_NT 10.0.26300 x64, AMD Ryzen AI 7 350 w/ Radeon 860M (16 hilos), 23.2 GB RAM; pruebas de caja negra con usuarios y datos únicos por ejecución (eliminados al finalizar).
- **Resultado global:** 48/53 casos aprobados (5 fallidos) · 11 hallazgos (Media: 3, Baja: 6, Informativa: 2)

## 1. Objetivo y alcance

Evaluar los controles de seguridad de la API REST de TaskFlow (NestJS + PostgreSQL) mediante pruebas de caja negra automatizadas contra el backend en ejecución, complementadas con revisión del código fuente, verificación de solo lectura en la base de datos y análisis de dependencias (`npm audit`). Cada caso está mapeado a OWASP Top 10 2021 y OWASP API Security Top 10 2023 e incluye casos positivos (el uso legítimo funciona) y negativos (el ataque es bloqueado).

Controles verificados: guard JWT, firma/algoritmo/expiración del token, bloqueo por fuerza bruta (5 intentos → 429 durante 15 min), mensajes genéricos de login, autorización por pertenencia al equipo y por rol de líder, `select:false` + bcrypt para contraseñas, ValidationPipe (whitelist, MaxLength, IsUUID), ParseUUIDPipe, consultas parametrizadas de TypeORM, helmet, CORS restringido y gestión de secretos.

## 5. Interpretación de resultados

- **Autenticación:** el guard JWT es sólido: todas las rutas protegidas exigen token y se rechazan tokens con firma alterada, payload manipulado, `alg: none`, secretos adivinados y tokens caducados. El bloqueo por fuerza bruta funciona: el 6.º intento devuelve 429 incluso con la contraseña correcta, sin afectar a otras cuentas. El mensaje de error del login es idéntico para usuario inexistente y contraseña incorrecta. El tiempo de respuesta tampoco distingue cuentas existentes (bcrypt.compare se ejecuta siempre, con un hash ficticio si el correo no existe). El limitador es por correo, no por IP, por lo que no frena el *password spraying*. La política de contraseñas (mínimo 8 caracteres con al menos una letra y un número) rechaza contraseñas triviales como "123456", "password" o "aaaaaa". El token de una cuenta eliminada devuelve 401.
- **Autorización:** no se encontraron BOLA/IDOR: un usuario ajeno recibe 403 en lectura y escritura sobre equipos, proyectos, listas y tareas de otros, los datos quedan intactos, las acciones de líder están protegidas (403 para miembros) y la expulsión de un miembro revoca el acceso de inmediato porque la autorización se calcula en cada petición. Un detalle menor: los recursos inexistentes devuelven 404 y los ajenos 403, lo que permite saber si un UUID existe (impacto bajo al ser UUID v4 no adivinables).
- **Exposición de datos:** ninguna de las respuestas analizadas en toda la ejecución contiene la contraseña ni el hash; en la BD las contraseñas están almacenadas con bcrypt `$2b$10$` (60 caracteres). La búsqueda `GET /usuarios?email=` y el 409 del registro permiten enumerar correos registrados.
- **Inyección:** los payloads SQLi no alteran las consultas (TypeORM usa parámetros `:email`) y se almacenan como texto literal. El XSS almacenado se devuelve como dato JSON y React lo escapa al renderizar (no hay `dangerouslySetInnerHTML`). 
- **Validación:** los límites de longitud (255/5000/72) y el formato UUID se validan con mensajes en español. El ValidationPipe **elimina** silenciosamente los campos no permitidos (whitelist) en lugar de rechazarlos con 400, lo que mitiga el *mass assignment* (no se pudo fijar id, liderId, listaId ni estado) pero oculta peticiones manipuladas. Los cuerpos > 100 KB se rechazan con 413.
- **Configuración:** helmet aplica CSP, HSTS, nosniff, X-Frame-Options y Referrer-Policy, y no se envía X-Powered-By. CORS solo autoriza a http://localhost:5173. Los errores (incluido el 500) no filtran trazas. El fichero `.env` está ignorado y fuera del índice de git (ver `git-secretos.txt`; si estuvo versionado antes, el historial conserva los secretos y conviene rotarlos). El frontend (servidor de desarrollo Vite) no define CSP y guarda el JWT en localStorage.
- **Dependencias:** SEG-DEP-01 (Fallido) → crítica=0, alta=4, moderada=7, baja=0 (total 11). Críticas/altas: @nestjs/platform-express (high, directa), body-parser (high), lodash (high), multer (high) · SEG-DEP-02 (Aprobado) → crítica=0, alta=8, moderada=13, baja=3 (total 24) · SEG-DEP-03 (Fallido) → crítica=0, alta=2, moderada=3, baja=1 (total 6). Críticas/altas: follow-redirects (high), vite (high, directa). Las vulnerabilidades restantes del backend proceden sobre todo de NestJS 10/Express 4 (@nestjs/platform-express, multer, lodash…), cuya corrección requiere actualizar NestJS a una versión mayor; las pruebas no modifican dependencias.

## 6. Conclusión

Los controles centrales (autenticación JWT, autorización por equipo/rol, hashing, validación e inyección) son efectivos frente a los ataques probados. Quedan 5 caso(s) no superado(s), que se documentan como hallazgos/recomendaciones: SEG-AUTH-13 (Limitación por cliente/IP frente a password spraying); SEG-DATA-03 (Búsqueda de usuarios por email no permite enumerar cuentas ajenas); SEG-CONF-06 (El frontend define Content-Security-Policy); SEG-DEP-01 (Dependencias de producción del backend sin vulnerabilidades críticas/altas); SEG-DEP-03 (Dependencias del frontend — npm audit). Se recomienda priorizar los hallazgos de severidad Alta y Media de la sección 4.
